# TMS 运输管理系统项目架构设计文档

## 1. 文档说明

### 1.1 文档目的

本文档用于指导 TMS 运输管理系统的后续详细设计、工程搭建、编码开发、测试、部署和持续演进。文档以企业级项目标准为目标，强调工程规范、模块边界、可维护性、可扩展性、安全性、可观测性和交付效率。

本文档不是业务需求文档，而是面向研发团队的架构与工程落地指南。后续开发时，应优先遵循本文档约定；如确需调整，应同步更新本文档或补充 ADR 架构决策记录。

### 1.3 架构定位

本项目采用“微服务架构”作为目标架构，后端按照业务能力拆分为多个独立服务，前端通过统一网关访问后端能力。

选择微服务架构的原因：

- TMS 业务天然存在清晰边界，例如认证权限、基础资料、订单、调度、运输执行、异常、费用结算、文件、报表。
- 不同业务域的扩展频率、性能压力、数据模型和团队职责不同，适合独立开发、测试、部署和扩容。
- 订单、运输、结算等核心链路需要通过事件驱动方式解耦，减少同步调用造成的级联影响。
- 企业级系统需要支持后续多团队并行开发、独立发布、灰度上线和服务级监控。
- 微服务可以为后续 GPS 接入、外部系统集成、移动端、报表计算等能力预留独立演进空间。

微服务建设原则：

- 服务按业务能力拆分，不按技术层拆分。
- 每个微服务拥有自己的数据库 schema 或独立数据库，禁止跨服务直接访问对方数据表。
- 服务间同步调用通过 REST 或 gRPC，异步解耦通过 RabbitMQ 事件。
- 统一入口通过 API Gateway / Nginx，对外隐藏内部服务拓扑。
- 本地开发阶段通过 Docker Compose 管理服务和中间件，生产阶段可演进到 Kubernetes。
- 微服务数量要受控，一期优先拆分核心边界，避免为了拆分而拆分。

### 2.3 微服务拆分

一期建议拆分以下服务：

| 服务 | 职责 | 数据边界 |
| --- | --- | --- |
| tms-gateway | 统一入口、鉴权前置、路由转发、限流、请求日志、聚合查询 | 不持有核心业务数据 |
| tms-auth-service | 登录、令牌、用户会话、权限校验 | sys_user、sys_role、sys_permission |
| tms-system-service | 字典、菜单、组织、操作日志、系统配置 | sys_dict、sys_menu、sys_org、sys_operation_log |
| tms-base-service | 客户、承运商、车辆、司机、线路、站点 | base_customer、base_carrier、base_vehicle、base_driver |
| tms-order-service | 运输订单、货物明细、订单状态机 | tms_order、tms_order_cargo、tms_order_status_history |
| tms-dispatch-service | 调度计划、派车、承运商分配 | tms_dispatch_plan、tms_dispatch_vehicle |
| tms-transport-service | 运输任务、发车、在途节点、签收、回单 | tms_transport_task、tms_transport_node、tms_receipt |
| tms-exception-service | 异常上报、异常处理、异常关闭 | tms_exception、tms_exception_log |
| tms-finance-service | 应收、应付、对账、结算 | fin_receivable、fin_payable、fin_statement、fin_settlement |
| tms-file-service | 文件上传、下载、MinIO 元数据、访问权限 | file_object |
| tms-report-service | 统计报表、异步报表任务、汇总表 | report_*、sys_async_task |
| tms-integration-service | ERP、WMS、GPS、财务系统等外部集成 | integration_* |

服务拆分约束：

- 服务内可以使用分层架构，服务间不能共享 repository。
- 服务间不能通过数据库表耦合，只能通过 API、事件或只读报表模型集成。
- 跨服务业务流程使用 Saga / 状态补偿 / 事件驱动，不使用跨库分布式事务作为默认方案。
- 高频读场景可以通过报表服务或查询模型做数据冗余，但必须标记数据来源和刷新策略。

### 2.4 设计原则

- 高内聚：每个微服务内部包含自己的接口、应用服务、领域规则、仓储、模型和 DTO。
- 低耦合：服务之间通过 API 契约或领域事件交互，禁止直接跨服务访问数据库表。
- 事务清晰：涉及多表写入的业务由应用服务统一开启事务。
- 状态受控：订单、调度、运输任务、异常、结算等状态变化必须通过明确的状态流转方法完成。
- 接口稳定：对外 API 路径和响应结构保持稳定，破坏性变更通过版本升级处理。
- 配置外置：数据库、缓存、消息队列、密钥等通过环境变量或配置文件注入。
- 默认安全：认证、授权、数据权限、审计日志作为基础能力建设。
- 可观测：所有请求、任务、消息和关键业务操作都能通过 traceId 追踪。
- 可测试：核心业务逻辑可以脱离 HTTP 层进行单元测试。

## 4. 后端架构设计

### 4.1 后端启动流程

```text
main.go
  -> 加载配置
  -> 初始化日志
  -> 初始化数据库连接池
  -> 初始化 Redis
  -> 初始化 RabbitMQ
  -> 初始化 MinIO
  -> 初始化 ID 生成器
  -> 初始化 Validator
  -> 创建依赖容器
  -> 注册本服务路由和中间件
  -> 注册全局中间件
  -> 注册路由
  -> 启动 HTTP Server
  -> 监听退出信号
  -> 优雅关闭
```

### 4.2 应用依赖容器

后端不建议在业务代码中使用全局变量直接访问数据库、Redis 或配置。推荐通过应用依赖容器集中管理。

示例结构：

```go
type AppContext struct {
    Config     *config.Config
    Logger     *zap.Logger
    DB         *gorm.DB
    Redis      *redis.Client
    MQ         rabbitmq.Client
    MinIO      minio.Client
    IDGen      idgen.Generator
    Validator  *validator.Validate
}
```

要求：

- Handler 依赖 Service 接口。
- Service 依赖 Repository 接口。
- Repository 依赖数据库连接。
- 基础设施对象由 bootstrap 创建。
- 不允许业务层自行创建数据库连接或消息队列连接。

### 4.3 分层调用方向

合法调用方向：

```text
api -> service -> repository -> database
api -> dto
service -> domain
service -> event
service -> repository
repository -> model
```

禁止调用方向：

```text
repository -> service
model -> service
domain -> api
api -> repository
跨服务直接调用对方 repository
跨服务直接修改对方业务表
```

### 4.4 Handler 设计规范

Handler 只处理 HTTP 相关逻辑：

- 解析请求参数。
- 调用参数校验。
- 获取当前登录用户。
- 调用 Service。
- 返回统一响应。

Handler 不做：

- 不写业务规则。
- 不直接操作数据库。
- 不拼接复杂 SQL。
- 不控制复杂事务。
- 不直接发送消息队列。

示例：

```go
func (h *OrderHandler) Create(c *gin.Context) {
    var req dto.CreateOrderRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, errors.BadRequest(err))
        return
    }

    currentUser := middleware.CurrentUser(c)
    result, err := h.orderService.Create(c.Request.Context(), currentUser, req)
    if err != nil {
        response.Fail(c, err)
        return
    }

    response.Success(c, result)
}
```

### 4.5 Service 设计规范

Service 是业务编排核心，负责：

- 校验业务前置条件。
- 调用领域规则。
- 控制事务。
- 调用多个 Repository。
- 发布领域事件。
- 记录关键业务日志。

示例：

```go
func (s *orderService) Submit(ctx context.Context, user auth.CurrentUser, orderID string) error {
    return s.txManager.WithTx(ctx, func(txCtx context.Context) error {
        order, err := s.orderRepo.GetForUpdate(txCtx, orderID)
        if err != nil {
            return err
        }

        if err := order.CanSubmit(); err != nil {
            return err
        }

        order.Submit(user.UserID)

        if err := s.orderRepo.UpdateStatus(txCtx, order); err != nil {
            return err
        }

        return s.eventPublisher.PublishAfterCommit(txCtx, event.OrderSubmitted{
            OrderID: order.ID,
            UserID:  user.UserID,
        })
    })
}
```

### 4.6 Repository 设计规范

Repository 负责数据访问，提供面向业务语义的方法。

推荐方法命名：

```go
Create(ctx context.Context, entity *Order) error
Update(ctx context.Context, entity *Order) error
GetByID(ctx context.Context, id string) (*Order, error)
GetForUpdate(ctx context.Context, id string) (*Order, error)
List(ctx context.Context, query OrderQuery) ([]Order, int64, error)
ExistsByOrderNo(ctx context.Context, orderNo string) (bool, error)
```

Repository 要求：

- 不返回 ORM 内部错误给上层，应转换为项目统一错误。
- 查询必须支持 context。
- 列表查询必须分页。
- 更新关键状态时应校验版本号或加行锁。
- 不在 Repository 中写复杂业务规则。

### 4.7 事务管理

需要事务的场景：

- 创建订单及订单货物明细。
- 调度计划生成运输任务。
- 签收后生成应收、应付费用。
- 费用复核后生成对账单。
- 对账单确认后生成结算单。
- 状态变更和状态历史记录需要同时写入。

事务设计原则：

- 事务入口放在 Service。
- 不在 Handler 开启事务。
- 不在 Repository 内部隐式开启业务事务。
- 同一事务内所有 Repository 使用同一个 tx context。
- 事务内只做数据库必要操作，外部 HTTP 调用、文件上传、消息投递应放在事务外或使用 outbox 模式。

建议封装：

```go
type TxManager interface {
    WithTx(ctx context.Context, fn func(ctx context.Context) error) error
}
```

### 4.8 状态机设计

订单、调度计划、运输任务、异常、结算单都必须使用状态机思想管理。

订单状态流转：

```text
draft
  -> submitted
  -> pending_dispatch
  -> dispatched
  -> in_transit
  -> signed
  -> settled

draft -> cancelled
submitted -> cancelled
pending_dispatch -> cancelled
```

运输任务状态流转：

```text
pending
  -> loaded
  -> departed
  -> in_transit
  -> arrived
  -> signed
  -> closed

departed -> exception
in_transit -> exception
exception -> in_transit
exception -> closed
```

状态机要求：

- 所有状态变化必须记录状态历史。
- 状态变化必须包含操作人、操作时间、来源、备注。
- 不允许通过通用更新接口直接修改状态字段。
- 每个状态变化都应有独立业务方法，例如 `SubmitOrder`、`CancelOrder`、`DepartTask`、`SignTask`。

状态历史表建议：

```text
tms_status_history
  id
  biz_type
  biz_id
  from_status
  to_status
  action
  operator_id
  operator_name
  remark
  created_at
```

### 4.9 领域事件设计

领域事件用于解耦模块之间的后续动作。

典型事件：

| 事件 | 触发时机 | 消费方 |
| --- | --- | --- |
| OrderSubmitted | 订单提交 | 调度模块、通知模块 |
| DispatchPlanCreated | 调度计划创建 | 运输任务模块 |
| TransportDeparted | 车辆发车 | 订单模块、通知模块 |
| TransportSigned | 运输签收 | 费用模块、回单模块 |
| ExceptionReported | 异常上报 | 通知模块、工作台 |
| StatementConfirmed | 对账确认 | 结算模块 |

事件处理策略：

- 事务内写业务数据。
- 事务后发布事件。
- 重要事件使用 outbox 表保证可靠投递。
- 消费者幂等处理。
- 事件体包含业务 ID，不传递完整大对象。

Outbox 表建议：

```text
event_outbox
  id
  event_type
  aggregate_type
  aggregate_id
  payload
  status
  retry_count
  next_retry_at
  created_at
  updated_at
```

### 4.10 异步任务设计

适合异步处理的任务：

- 导入订单 Excel。
- 导出订单报表。
- 生成统计报表。
- 发送通知。
- 生成费用。
- 同步第三方系统。
- 清理临时文件。

异步任务要求：

- 任务有唯一 ID。
- 任务状态可查询。
- 任务失败记录错误原因。
- 支持重试次数和下次重试时间。
- 消费者必须幂等。
- 大任务拆分为小批次执行。

任务表建议：

```text
sys_async_task
  id
  task_type
```

### 4.11 微服务治理设计

#### 4.11.1 服务通信

服务间通信分为同步调用和异步事件：

| 通信方式 | 使用场景 | 示例 |
| --- | --- | --- |
| REST | 前端调用、网关转发、简单服务查询 | 网关查询订单详情 |
| gRPC | 服务内部高频同步调用、低延迟调用 | 调度服务校验车辆状态 |
| RabbitMQ 事件 | 状态通知、最终一致性、异步任务 | 运输签收后通知财务生成费用 |

同步调用要求：

- 必须设置超时时间。
- 必须传递 traceId。
- 必须定义错误码映射。
- 必须避免长链路嵌套调用。
- 非核心依赖失败时要有降级或明确错误。

异步事件要求：

- 事件必须有 eventId、eventType、aggregateId、occurredAt、traceId。
- 消费端必须按 eventId 做幂等。
- 事件投递失败进入重试或死信队列。
- 关键业务事件通过 outbox 模式保证可靠投递。

#### 4.11.2 服务注册与发现

本地 Docker Compose 阶段：

- 使用 Docker Compose service name 作为服务发现名称。
- 例如 `http://order-service:8080`、`http://finance-service:8080`。

生产 Kubernetes 阶段：

- 使用 Kubernetes Service 做服务发现。
- 服务名建议保持稳定，例如 `tms-order-service`。
- 对外入口统一走 Ingress / API Gateway。

#### 4.11.3 配置中心

一期：

- 使用环境变量和配置文件。
- 每个服务有自己的 `.env` 或 config。
- 公共配置通过模板维护，敏感配置不入库。

后续：

- 可接入 Nacos、Consul、Apollo 或 Kubernetes ConfigMap / Secret。
- 配置变更需要审计。
- 关键配置变更需要灰度和回滚方案。

#### 4.11.4 熔断、限流与重试

网关层：

- 对登录、导出、批量操作等接口限流。
- 对异常 IP 或高频请求限流。

服务调用层：

- 设置连接超时、读写超时。
- 对可重试错误使用有限次数重试。
- 对不可重试错误直接失败。
- 避免无界重试造成雪崩。

消息消费层：

- 消费失败记录原因。
- 按重试次数退避。
- 超过上限进入死信队列。
- 支持人工重新投递。

#### 4.11.5 分布式事务与一致性

微服务架构不默认使用跨库强事务。TMS 核心流程采用本地事务 + 领域事件 + 补偿机制。

示例：签收生成费用

```text
transport-service 本地事务
  -> 更新运输任务为已签收
  -> 写入签收记录
  -> 写入 event_outbox: TransportSigned

outbox worker
  -> 发布 TransportSigned 到 RabbitMQ

finance-service 消费事件
  -> 幂等校验 eventId
  -> 根据运输任务和订单快照生成应收应付
  -> 记录费用生成结果
```

一致性要求：

- 业务主状态由所属服务负责。
- 其他服务需要的数据通过事件同步、API 查询或报表模型获取。
- 补偿动作必须显式记录，不能静默修正。
- 所有跨服务命令都要考虑重复、乱序、延迟和失败。

## 6. 数据库架构设计

### 6.1 PostgreSQL 使用原则

- 所有业务表使用 `id` 主键。
- 主键建议使用 UUID、ULID 或雪花 ID，项目内保持统一。
- 所有表包含 `created_at`、`updated_at`。
- 需要软删除的表包含 `deleted_at`。
- 关键表包含 `created_by`、`updated_by`。
- 金额字段使用 `numeric(18,2)`。
- 重量、体积、里程等使用 `numeric`。
- 状态字段使用 `varchar`，不要使用裸数字。
- JSON 扩展字段使用 `jsonb`。
- 所有外键关系在应用层和数据库层都要明确，是否创建数据库外键根据性能和运维策略决定。
- 禁止无分页查询大表。

### 7.3 缓存策略

字典缓存：

- 读取时先查 Redis。
- 未命中查数据库并写入 Redis。
- 字典修改后删除缓存。
- 设置合理过期时间。

- 用户登录后可缓存权限集合。
- 用户角色或权限变更后清理相关用户缓存。
- 权限校验失败时可回源数据库确认，避免缓存不一致导致误判。

分布式锁：

- 必须设置过期时间。
- 加锁值使用随机 token。
- 解锁时校验 token。
- 不把长耗时任务放在短锁里。

```text
  -> 生成 access token 和 refresh token
  -> 返回用户基础信息和权限摘要
  -> 前端保存 token
  -> 后续请求携带 Authorization
```

请求头：

```text
Authorization: Bearer <access_token>
```

### 11.2 RBAC 权限模型

```text
用户 sys_user
  -> 用户角色 sys_user_role
  -> 角色 sys_role
  -> 角色权限 sys_role_permission
  -> 权限 sys_permission
```

权限类型：

- 菜单权限。
- 按钮权限。
- API 权限。
- 数据权限。

### 11.3 数据权限

TMS 常见数据权限：

- 全部数据。
- 所属组织及下级组织。
- 所属组织数据。
- 仅本人创建数据。
- 指定客户数据。
- 指定承运商数据。

实现建议：

- 当前用户上下文包含组织、角色、数据范围。
- Repository 查询接收 DataScope 条件。
- 不允许前端传入数据权限条件后直接信任。
- 数据权限统一封装，避免散落在业务代码中。

### 11.4 操作审计

需要审计的操作：

- 登录、退出。
- 新增、修改、删除基础资料。
- 订单提交、取消。
- 创建调度计划。
- 发车、签收。
- 异常处理。
- 费用确认、对账、结算。
- 用户、角色、权限变更。

审计字段：

```text
operator_id
operator_name
module
action
biz_type
biz_id
request_method
request_path
request_body
client_ip
user_agent
result
error_message
created_at
```

### 11.5 安全要求

- 密码使用 bcrypt 或 Argon2 哈希。
- 登录失败次数限制。
- JWT 设置合理过期时间。
- refresh token 可撤销。
- 敏感接口必须鉴权。
- 后端禁止信任前端传入的用户 ID、组织 ID、权限数据。
- 文件上传做大小、类型、后缀校验。
- SQL 查询使用参数化，禁止拼接用户输入。
- 生产环境关闭 debug 日志和 Swagger 公开访问。
- CORS 白名单配置化。

## 17. 编码规范

### 17.1 Go 编码规范

要求：

- 使用 `gofmt` 格式化。
- 使用 `go vet` 检查。
- 包名小写、简短、有业务含义。
- 接口定义在使用方附近。
- error 必须处理。
- context 放在函数第一个参数。
- 不在业务代码中 panic。
- 不吞掉错误。
- 不返回含糊的 `errors.New("error")`。

命名建议：

```go
type OrderService interface {}
type OrderRepository interface {}
type CreateOrderRequest struct {}
type OrderListResponse struct {}
```

### 17.2 TypeScript 编码规范

要求：

- 开启 strict。
- API 类型显式定义。
- 组件 props 和 emits 显式声明。
- 避免 any。
- 公共逻辑抽到 composable。
- 页面组件不堆积过多业务工具函数。
- 请求错误统一处理。

### 17.3 SQL 编码规范

要求：

- SQL 关键字小写或大写保持一致。
- 禁止 `select *` 用于核心查询。
- 查询必须考虑分页。
- 大表更新必须带条件。
- 删除业务数据默认软删除。
- migration 文件一经合并不随意修改，新增变更使用新 migration。

## 21. 风险控制

| 风险 | 表现 | 控制措施 |
| --- | --- | --- |
| 状态流转混乱 | 订单状态与运输任务状态不一致 | 状态机、状态历史、统一状态变更入口 |
| 模块耦合严重 | 一个模块直接改另一个模块的表 | 服务接口、领域事件、代码评审 |
| 报表拖慢业务库 | 大查询影响订单操作 | 索引、异步报表、汇总表、读库 |
| 权限遗漏 | 用户看到不该看的数据 | RBAC、数据权限、接口鉴权测试 |
| 重复提交 | 重复订单、重复签收、重复结算 | 幂等 key、唯一约束、乐观锁 |
| 文件不可控 | 附件丢失或泄漏 | MinIO、元数据表、权限下载 |
| 配置泄漏 | 密码提交到仓库 | .env.example、secret 管理、代码扫描 |
| 部署不可重复 | 环境差异导致问题 | Docker Compose、migration、CI/CD |

```go
func RegisterRoutes(r *gin.Engine, deps *bootstrap.Dependencies) {
    api := r.Group("/api/v1")

    api.GET("/health", deps.HealthHandler.Health)
    api.GET("/ready", deps.HealthHandler.Ready)

    authGroup := api.Group("/auth")
    {
        authGroup.POST("/login", deps.AuthHandler.Login)

    secured := api.Group("")
    secured.Use(middleware.Auth(deps.TokenService))
    secured.Use(middleware.RBAC(deps.PermissionService))

        dispatch.RegisterRoutes(secured, deps.DispatchHandler)
        transport.RegisterRoutes(secured, deps.TransportHandler)
        finance.RegisterRoutes(secured, deps.FinanceHandler)
    }
}
```

## 27. 附录：前端接口封装示例

```ts
import axios from 'axios'

export const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 15000,
})

request.interceptors.request.use((config) => {
  const token = localStorage.getItem('access_token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})

request.interceptors.response.use(
  (response) => {
    const body = response.data
    if (body.code === 0) {
      return body.data
    }
    return Promise.reject(body)
  },
  (error) => Promise.reject(error),
)
```

## 28. 结语

本架构设计以“微服务清晰拆分、核心链路稳定落地、服务治理逐步增强”为核心思路。项目初期应控制服务数量，把重点放在服务边界、状态一致性、权限安全、数据质量、可观测性和自动化交付上。

只要后续开发严格遵循本文档的微服务边界、接口契约、事件规范、数据库隔离、权限控制和测试要求，TMS 系统就可以在保持开发效率的同时具备企业级系统所需的可维护性和可扩展性。
