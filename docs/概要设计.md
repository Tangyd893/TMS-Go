# TMS 运输管理系统概要设计

## 1. 文档目的

本文档用于描述 TMS（Transportation Management System，运输管理系统）的总体设计方案，为后续需求细化、数据库设计、接口设计、前后端开发、测试与部署提供统一依据。

系统采用前后端分离架构：

- 后端：Golang
- 前端：Vue
- 数据库：PostgreSQL
- 中间件：通过 Docker / Docker Compose 统一管理

## 2. 建设目标

TMS 系统面向企业运输业务全流程管理，覆盖从客户下单、运输计划、车辆调度、在途跟踪、签收回单、费用结算到统计分析的核心业务闭环。

主要目标：

- 统一管理运输订单、客户、车辆、司机、承运商、线路等基础与业务数据。
- 支持订单调度、派车、装车、发车、运输跟踪、签收、异常处理等流程。
- 支持运输费用计算、应收应付结算、对账与财务数据导出。
- 提供清晰的权限控制、操作日志、业务状态流转记录。
- 支持容器化部署，降低本地开发、测试、生产环境的一致性成本。

## 3. 系统边界

### 3.1 系统范围

本系统主要包含以下能力：

- 运输订单管理
- 调度计划管理
- 车辆与司机管理
- 承运商管理
- 线路与站点管理
- 在途跟踪与节点回传
- 异常事件管理
- 回单与签收管理
- 费用与结算管理
- 报表统计
- 系统管理与权限控制

### 3.2 暂不纳入一期范围

以下能力可作为二期或扩展模块建设：

- 深度路径优化算法
- 实时 GPS 硬件设备直连
- 与 ERP、WMS、财务系统的复杂双向集成
- 移动端原生 App
- 多租户 SaaS 商业化能力

## 4. 总体架构

### 4.1 架构风格

系统采用前后端分离 + 微服务架构。前端通过统一网关访问后端能力，后端按业务领域拆分为认证权限、基础资料、订单、调度、运输执行、异常、费用结算、文件、报表等多个微服务。

对外统一使用 RESTful API；服务内部可根据场景使用 REST、gRPC 或 RabbitMQ 事件通信。一期本地开发和测试环境通过 Docker Compose 编排微服务与中间件，后续生产环境可演进到 Kubernetes。

```text
用户浏览器
    |
    | HTTPS
    v
Nginx / API Gateway / 静态资源服务
    |
    | REST API
    v
Golang 微服务集群
    |
    +---- tms-auth-service
    +---- tms-system-service
    +---- tms-base-service
    +---- tms-order-service
    +---- tms-dispatch-service
    +---- tms-transport-service
    +---- tms-exception-service
    +---- tms-finance-service
    +---- tms-file-service
    +---- tms-report-service
    |
    +---- PostgreSQL schemas / databases
    +---- Redis
    +---- RabbitMQ
    +---- MinIO
```

微服务拆分原则：

- 按业务能力拆分服务，不按技术层拆分服务。
- 每个微服务拥有独立的数据边界，禁止跨服务直接访问数据库表。
- 同步调用用于强实时查询和简单命令，异步事件用于状态通知、费用生成、报表统计、外部系统同步。
- 跨服务流程采用 Saga、事件补偿和幂等机制，不默认使用跨库分布式事务。

## 5. 后端概要设计

### 5.1 后端分层

每个 Golang 微服务内部建议采用清晰的分层结构：

```text
services/{service-name}/
cmd/                 服务程序入口
internal/
  api/               HTTP 路由、控制器、请求响应 DTO
  middleware/        鉴权、日志、跨域、限流等中间件
  service/           业务编排与业务规则
  repository/        数据访问
  model/             数据模型
  domain/            领域对象、状态机、枚举
  pkg/               内部通用工具
configs/             配置文件
migrations/          数据库迁移脚本
```

### 5.2 后端核心职责

- 网关服务提供统一 API 入口，业务微服务提供各自领域能力。
- 管理业务状态流转，例如订单待调度、已调度、运输中、已签收、已结算。
- 处理权限鉴定、数据权限和操作审计。
- 与 PostgreSQL、Redis、RabbitMQ、MinIO 等基础设施交互。
- 处理导入导出、异步任务、通知事件等非同步业务。
- 通过 RabbitMQ 发布和订阅领域事件，降低订单、调度、运输、结算之间的同步耦合。

### 5.3 API 设计原则

- 使用 RESTful 风格。
- 使用统一响应结构。
- 使用统一错误码。
- 对分页、排序、筛选参数进行标准化。
- 所有写操作记录操作日志。
- 关键业务状态变更通过专门接口完成，避免直接更新状态字段。

统一响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "018f2f9e-xxxx"
}
```

分页响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 100,
    "page": 1,
    "pageSize": 20
  }
}
```

## 7. 核心业务模块

### 7.1 订单管理

运输订单是系统的核心业务对象。

主要功能：

- 创建运输订单
- 查询订单列表
- 查看订单详情
- 编辑未调度订单
- 取消订单
- 拆单、合单，作为扩展能力
- 订单状态流转记录

订单关键字段：

- 订单编号
- 客户
- 发货方、收货方
- 起点、终点
- 计划提货时间
- 计划送达时间
- 货物名称、数量、重量、体积
- 运输要求
- 订单状态

### 7.2 调度管理

调度模块负责将运输订单分配给车辆、司机或承运商。

主要功能：

- 查询待调度订单
- 创建调度计划
- 分配车辆与司机
- 分配承运商
- 生成派车单
- 调整调度计划
- 取消调度

调度状态：

- 待调度
- 已调度
- 已派车
- 已装车
- 已发车

### 7.3 运输执行

运输执行模块跟踪车辆从发车到签收的过程。

主要功能：

- 发车确认
- 节点到达确认
- 在途轨迹记录
- 异常上报
- 签收确认
- 上传回单

运输节点示例：

- 已提货
- 已发车
- 到达中转点
- 离开中转点
- 到达目的地
- 已签收

### 7.4 异常管理

异常管理用于记录运输过程中的问题并形成闭环。

异常类型：

- 车辆故障
- 交通延误
- 货损货差
- 客户拒收
- 地址异常
- 天气原因
- 其他异常

异常状态：

- 待处理
- 处理中
- 已解决
- 已关闭

### 7.5 费用结算

费用结算模块负责运输业务的应收、应付、对账和结算。

主要功能：

- 维护费用项目
- 根据规则生成应收费用
- 根据规则生成应付费用
- 创建客户对账单
- 创建承运商对账单
- 创建结算单
- 导出财务数据

费用类型：

- 运费
- 装卸费
- 等待费
- 过路费
- 保险费
- 异常赔付

## 8. 数据库概要设计

### 8.1 数据库设计原则

- 使用 PostgreSQL 作为主数据库。
- 所有业务主表使用 `id` 作为主键，建议采用 UUID 或雪花 ID。
- 所有表包含 `created_at`、`updated_at`、`deleted_at` 字段。
- 关键业务表包含 `created_by`、`updated_by` 字段。
- 枚举值使用字典表或代码枚举统一管理。
- 金额字段使用 `numeric(18,2)`。
- 重量、体积等度量字段使用 `numeric`，避免浮点误差。
- 高频查询字段建立索引。
- 重要业务状态变化单独记录历史表。

### 9.2 Docker Compose 目录建议

```text
docker/
  docker-compose.yml
  nginx/
    nginx.conf
  postgres/
    init/
  minio/
    data/
```

### 9.3 Docker Compose 管理原则

- 本地开发、测试环境统一通过 Docker Compose 启动中间件。
- 应用配置通过环境变量注入。
- 数据库数据、MinIO 文件数据使用 Docker volume 持久化。
- 密码、密钥等敏感信息不提交到代码仓库。
- 开发环境和生产环境使用不同的 `.env` 文件。
- 生产环境建议结合 CI/CD、镜像仓库和独立的部署配置。

## 10. 权限与安全设计

### 10.1 认证方式

- 使用用户名密码登录。
- 登录成功后签发 JWT。
- 前端在请求头中携带 `Authorization: Bearer <token>`。
- 后端通过认证中间件校验令牌。

### 10.2 权限模型

采用 RBAC 权限模型：

```text
用户 -> 角色 -> 权限 -> 菜单 / 按钮 / 接口
```

权限粒度：

- 菜单权限
- 按钮权限
- 接口权限
- 数据权限

### 10.3 安全要求

- 密码使用 bcrypt 或 Argon2 哈希存储。
- 所有写接口校验登录态与权限。
- 重要操作记录操作日志。
- 文件上传限制文件大小和文件类型。
- 防止 SQL 注入、XSS、越权访问。
- 生产环境启用 HTTPS。

## 13. 关键业务流程

### 13.1 订单到签收流程

```text
创建订单
  -> 提交订单
  -> 待调度
  -> 创建调度计划
  -> 分配车辆与司机
  -> 生成运输任务
  -> 装车
  -> 发车
  -> 在途节点回传
  -> 到达目的地
  -> 签收
  -> 上传回单
  -> 生成费用
  -> 对账结算
```

### 13.2 异常处理流程

```text
运输任务执行中
  -> 上报异常
  -> 记录异常类型、描述、图片附件
  -> 指派处理人
  -> 处理异常
  -> 填写处理结果
  -> 关闭异常
```

### 13.3 费用结算流程

```text
订单签收
  -> 根据计费规则生成应收/应付
  -> 财务复核费用
  -> 创建对账单
  -> 客户或承运商确认
  -> 创建结算单
  -> 标记结算完成
```

## 14. 非功能设计

### 14.1 性能要求

- 普通列表查询响应时间控制在 1 秒以内。
- 复杂统计查询响应时间控制在 3 秒以内。
- 高频列表必须支持分页、条件筛选与索引优化。
- 大批量导入导出采用异步任务。

### 14.2 可用性要求

- 每个后端微服务提供健康检查。
- 中间件数据卷持久化。
- 关键业务操作具备重试或补偿机制。
- 异步任务失败需要记录失败原因并支持重新执行。

### 14.3 可维护性要求

- 模块边界清晰。
- 状态枚举集中管理。
- 数据迁移脚本版本化。
- 接口文档与代码保持同步。
- 关键业务逻辑增加单元测试。

## 16. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 业务状态复杂 | 容易出现状态不一致 | 使用状态机思想，状态变更统一入口 |
| 调度规则变化频繁 | 影响开发效率 | 将调度规则与执行流程解耦 |
| 报表查询慢 | 影响用户体验 | 增加索引、异步汇总、报表宽表 |
| 文件附件增长快 | 存储压力增加 | 使用 MinIO，并规划生命周期策略 |
| 权限边界复杂 | 容易越权 | RBAC + 数据权限 + 操作审计 |

## 17. 总结

本概要设计以 Golang 微服务 + Vue + PostgreSQL 为核心技术栈，通过 Docker Compose 统一管理 PostgreSQL、Redis、RabbitMQ、MinIO、Nginx 和各业务微服务，目标架构为企业级微服务体系。

一期建议优先完成网关、认证权限、基础资料、订单、调度、运输执行、签收、异常、费用结算等核心微服务，形成完整运输业务闭环。后续可根据业务规模逐步扩展移动端、GPS 对接、路径优化、外部系统集成和多租户能力。
